## 結論

**最小構成案は「既存の承認済みautomation runner＋集計・再実行制御用スクリプト1本＋既存共有フォルダー」です。** スプレッドシートはユーザー操作が必要なため、無人実行の経路には入れません。追加製品も使いません。

ただし、**この構成で要件を満たすには、出力を「重複させず、一括で、障害後も残る形で確定する」保存操作の保証が必要です。** 提示資料で確認できる共有フォルダーの機能は役割別アクセス制限だけであり、この保存操作の保証は未確認です。したがって、現時点では「最小構成案は示せるが、要件充足は検証前」という判定です。

## 1. 構成と役割

| 構成要素 | 担当する処理 |
|---|---|
| 既存のautomation runner | 毎日の定時起動、スクリプト実行、実行ログの保持。実行時刻・タイムゾーンと実行アカウントを固定する。 |
| 集計・再実行制御用スクリプト | CSVの検証、部署別集計、CSV生成、処理単位の識別、既存結果との照合、重複を防ぐ出力確定、ログ出力を実装する。 |
| 既存共有フォルダー | 入力、作業中データ、確定出力、再実行時の照合情報を保存する。各領域へのアクセスを役割別に制限する。 |

runnerの定時実行機能やログ保持機能を、重複防止機能の代わりにはしません。**重複防止はスクリプトの設計と保存先の保証を組み合わせて実現します。**

アクセス権は、入力提供者には受け渡し領域への必要な権限、集計用アカウントには確定入力の読み取りと作業・出力領域への必要な権限、結果利用者には確定出力の読み取りだけを付与します。作業中データは結果利用者に公開せず、受け渡し完了後の入力は処理中に変更されない状態にします。

## 2. 重複書き込みを防ぐ設計

**出力は処理単位ごとのCSVとし、既存CSVへ集計行を追記する方式は採りません。** 以下のように、同じ処理を何度起動しても確定結果が一つになる設計にします。

1. **再試行しても変わらない処理キーを使う。**  
   例えば「集計名＋対象業務日」です。翌日に再実行しても元の対象業務日を使い、実行時刻や実行IDで別処理にはしません。入力内容のハッシュと集計仕様の版も照合情報として保存し、同じキーで入力や仕様が変わった場合は自動上書きせず、訂正処理として扱います。

2. **完成するまで非公開領域に置く。**  
   集計CSVと、処理キー・入力ハッシュ・出力ハッシュ・入出力件数などの照合情報を、実行ごとの作業ディレクトリに作成します。検証が終わるまで確定出力として見せません。

3. **CSVと照合情報を一つの単位として確定する。**  
   処理キーに対応する確定先へ、**「確定先が存在しない場合だけ、全体を原子的に公開する」**操作を行います。ここでいう原子的とは、途中状態ではなく「未公開」か「全体が公開済み」のどちらかだけが見えることです。同時実行でも一つだけが確定でき、既存結果を置き換えないこと、および確定成功後の永続性が必要です。この操作が共有フォルダーで保証されるかを確認します。

4. **再実行ではログだけでなく確定結果を照合する。**  
   有効な確定結果があれば書き込みを省略し、「既確定のためスキップ」と記録します。未確定の作業データしかなければ再処理します。確定状態が不明、出力が破損、入力が不一致の場合は、成功扱いや無条件の再書き込みをせず異常として停止します。

この設計では、**「出力は確定したが、成功ログを残す前に停止した」場合も、再実行時に確定結果を検出できます。** 別途の処理済み台帳やデータベースは不要です。

なお、「ファイルがないことを確認してから書く」だけでは、確認と書き込みの間に別実行が入り込めます。また、「CSV保存後に別の処理済みフラグを保存する」だけでは、その間の障害に対応できません。

## 3. 検証方法と合格条件

| 検証対象 | 方法 | 合格条件 |
|---|---|---|
| 無人の定時実行 | 対話ユーザーをログアウトさせ、スプレッドシートを起動しない状態で予定時刻を迎える。 | runnerが所定の実行アカウントで起動し、入力読み取りから出力確定まで完了する。 |
| 集計の正確性・処理能力 | 部署別の期待値が既知の5万行CSVを使用。欠損部署、不正数値、引用符などを含む入力も試す。 | 部署別合計・全体合計・件数が期待値と一致し、不正入力の扱いが定義どおり。定めた完了期限内に処理できる。 |
| 確定前の障害 | 集計途中、作業ファイル作成途中、確定直前で強制終了して再実行する。 | 部分的な結果が公開されず、最終的な確定結果は一つだけになる。 |
| 確定直後の障害 | 出力確定直後、成功ログ記録前に停止して再実行する。 | 確定結果を照合してスキップし、結果の追加・追記・上書きをしない。 |
| 同時実行 | 同じ処理キーで二つの実行を重ねる。 | 一つだけが確定する。他方は既存結果を照合し、重複出力を作らない。 |
| 保存先の障害 | 確定処理の前後で接続断や実行ホストの再起動を発生させ、復旧後に再実行する。 | 有効な確定結果の有無を判定でき、部分公開・重複確定・不明状態での成功扱いが起きない。保存先の仕様上の保証も確認する。 |
| 同じキーでの入力変更 | 正常処理後、対象業務日を変えず入力内容を変更して再実行する。 | 不一致を検出して停止し、既存結果を無断で置き換えない。 |
| 実行ログの保持 | 成功・失敗・スキップ・強制終了を発生させ、runnerや実行ホストの再起動後にも確認する。保持期間の保証も確認する。 | 処理キー、実行ID、開始・終了または異常終了、件数、結果、失敗理由を追跡でき、必要期間にわたり参照できる。 |
| 入出力のアクセス制限 | 入力提供者、集計用アカウント、結果利用者、無権限ユーザーで読み取り・書き込みを試す。 | 許可した操作だけが成功する。公開後の出力の実効権限も正しく、結果利用者による改変や無権限アクセスが拒否される。 |

集計対象列、欠損・不正データの扱い、完了期限、ログ保持期間は受入条件として定める必要があります。**5万行を処理できる性能は、提示資料だけでは保証されないため、実測対象です。**

## 最終判定の条件

**保存先の原子的・重複不可・永続的な確定操作について仕様上の保証を確認し、上記試験に合格した場合に、この最小構成を採用します。**

その操作、または同等の耐障害性を持つ仕組みを承認済み環境内で確認できなければ、必須要件をすべて満たすとは判定できません。手動操作を挟んだり、runnerだけに任せたりして要件を緩める構成にはしません。

*環境機能の根拠：提示資料「Aggregation environment」revision r1、Available capabilities節。重複防止方式と検証項目は、その制約に基づく設計案です。*
