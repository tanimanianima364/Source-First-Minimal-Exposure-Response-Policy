## 結論

**最小構成は「既存の承認済み自動実行基盤＋集計スクリプト＋既存共有フォルダー」です。** 表計算は無人実行の経路には含めません。

ただし、**提示資料だけでは、全要件を満たせると断定できません。** 重複書き込み防止には、スクリプトの工夫だけでなく、既存環境で「同じ処理の結果を、競合や障害があっても一度だけ確定する」操作を実現できることが必要です。共有フォルダーについて確認できているのはアクセス制御であり、原子的な確定操作や障害時の永続化保証までは記載されていません。

根拠：提示資料『Aggregation environment』revision r1「Available capabilities」。以下の処理方式は、この条件に基づく設計案です。

## 1. 最小構成と役割

| 構成要素 | 担当する処理・要件 | 注意点 |
|---|---|---|
| 既存の承認済み自動実行基盤 | 毎日の定時起動、実行ログの保持 | 基盤自体には重複書き込み防止機能がない |
| 集計スクリプト | CSV検証、部署別集計、出力作成、再実行時の照合、重複確定の防止 | 既存の承認済み実行環境で動かす。表計算の画面操作には依存させない |
| 既存共有フォルダー | 入力、一時ファイル、確定出力・照合情報の保存、入出力の権限制御 | 安全な確定操作と永続化の性質を確認する必要がある |

表計算は、必要なら検証時の独立した集計結果の照合に利用できますが、本番処理には必須ではありません。追加製品や別のデータベースを前提にしない構成です。

### アクセス権限

専用の実行アカウントを使用し、共有フォルダーを入力・非公開の作業領域・確定出力に分けます。

入力担当には所定の入力投入権限、実行アカウントには処理対象入力の読み取りと作業・出力領域への必要な書き込み権限、結果利用者には確定出力の読み取りだけを与えます。結果利用者による出力の変更・削除や、一時ファイルへのアクセスは許可しません。

入力は「投入完了後に処理対象として確定し、その後は変更しない」運用にします。**投入途中のCSVを定時処理が読み始めないこと**も必要です。

## 2. 重複書き込みを防ぐ処理方式

### ① 再実行しても変わらない処理キーを決める

例えば、**「対象業務日＋対象データセットID」**を処理キーとします。翌日に再実行しても、元の対象業務日のキーを使用します。起動時刻や試行ごとの実行IDは処理キーにしません。

入力ファイルのハッシュと集計定義の版は、処理キーに対応する照合情報として記録します。同じキーなのに入力内容や集計定義が異なる場合は、単なる再実行とは扱わず、競合として停止します。訂正データを別名で自動追加し、同じ業務日の結果が二重に存在する状態を避けるためです。

### ② 非公開領域で集計・検証を完了させる

CSVを読み、部署別に集計して、一時領域に結果CSVを作成します。同時に、処理キー、入力ハッシュ、集計定義版、入力件数、部署数、出力ハッシュなどを含む照合用メタデータを作成します。

不正な数値や列不足などは、事前に決めた扱いに従って検出します。エラー行を黙って捨てて成功扱いにはしません。利用者には、検証途中の出力を見せません。

### ③ 結果と照合情報を一体として、一度だけ確定する

実装例は、結果CSVとメタデータを含む一時ディレクトリを、処理キーに対応する固定の出力先へ、**「既存の確定結果を置換せず、全体を原子的に公開する」**方式です。

必要な性質は次のとおりです。

- 確定前の途中状態が、確定出力として見えない。
- 同じキーで同時実行しても、確定に成功するのは一つだけ。
- 確定した結果と照合情報が、障害・再起動後も保持される。

**これらは共有フォルダーの既知の機能ではなく、確認が必要な条件です。** 操作名が「移動」や「リネーム」であるだけでは十分ではありません。実際の共有ストレージ上での仕様確認と障害試験が必要です。同等の排他・永続化手段が既存環境で使える場合は、それによる実装でも構いません。

### ④ 再実行では、確定済みの結果を確認して書き込まない

固定の出力先に有効な確定結果が存在し、入力・集計定義・出力の整合性を確認できた場合は、**出力を追加・上書きせず、処理済みとして終了**します。不整合や破損がある場合は停止し、自動的に上書きしません。

これにより、「出力確定後、成功ログを残す前に異常終了した」場合も、再実行時に重複出力を防げます。完了判定は成功ログの有無だけに依存させません。

単純な「ファイルの存在確認→書き込み」では、その間に別実行が書けるため不十分です。また、共有CSVへの追記方式も採用しません。確定結果と照合情報は、少なくとも再実行を許可する期間中は保持します。

## 3. 定時実行とログの設定

定時実行では、実行時刻、タイムゾーン、対象業務日の決め方、入力の到着締切を固定します。入力が未到着・未確定の場合は、空の集計結果を成功出力するのではなく、未処理として記録します。

各試行には別の試行IDを付け、同じ処理キーに紐付けて、開始・終了・失敗・再実行・処理済みによるスキップを自動実行基盤のログへ記録します。入力件数、部署数、処理時間、出力先、エラー理由も残し、CSV本文や不要な機密情報はログへ出しません。

ログの必要保存期間は提示されていないため、運用上の保存期間を定義したうえで、基盤の保持設定と保存容量がそれを満たすことを確認します。

## 4. 検証方法と合格条件

以下は実機で行う受入試験です。**5万行という行数だけで処理性能を保証せず、実データ相当の列幅・部署数・CSV形式で測定します。**

| 検証項目 | 試験方法 | 合格条件 |
|---|---|---|
| 集計の正確性・性能 | 期待値が既知の5万行CSVで実行。実運用相当の部署数、文字コード、引用符・フィールド内改行などを含める | 部署別合計・全体合計・件数が期待値と一致し、所定の完了時刻と資源上限を満たす |
| 無人の定時実行 | 対話ログインや表計算を起動しない状態で定時起動。実行環境の再起動後も確認 | 人手なしで起動し、認証・入力読み取り・集計・確定・ログ記録まで完了する |
| 同一入力の再実行 | 同じ処理キー・入力で複数回実行 | 確定出力は一つのまま。追記・上書きがなく、後続試行は処理済みとして記録される |
| 同時実行 | 同じキーで二つの試行を同時に起動する | 確定成功は一つだけ。もう一方は既存結果を照合し、重複出力しない |
| 確定前の障害 | 読み込み中、集計中、一時ファイル書き込み中に強制停止し、再実行する | 途中結果が確定出力として見えず、再実行後に正しい結果が一つだけ存在する |
| 確定時・確定直後の障害 | 確定操作中の接続断、確定後かつ成功ログ前の強制停止、共有ストレージ再起動を試す | 確定状態が「未確定」または「完全な確定結果」のどちらかに判別できる。確定済み結果は保持され、再実行しても二重確定しない |
| 入力・結果の不整合 | 同じキーで別内容の入力を渡す。未完成入力、不正CSV、破損した確定出力も試す | 不整合を検知して停止し、既存結果を無断で置換しない |
| ログ保持 | 成功・失敗・スキップを発生させ、再起動とログのローテーションを検証する | 必要な保存期間を満たし、処理キーと試行IDで経過を追跡できる |
| 入出力の権限制御 | 入力担当・実行アカウント・結果利用者の各権限で、読み取り・書き込み・削除を試す | 許可した操作だけが成功する。一時領域や公開後の出力について、継承権限による意図しないアクセスもない |

**採用判定は、特に「安全な一度だけの確定」「障害後の永続性」「5万行の処理性能」の確認後です。** 原子的な確定操作、または同等の排他・永続化手段が既存環境内で確認できない場合、追加製品が承認されていない現条件では、全要件を満たす構成は確定できません。自動実行基盤とログ保持を組み合わせただけで、重複防止まで満たしたとは扱わないことが重要です。
