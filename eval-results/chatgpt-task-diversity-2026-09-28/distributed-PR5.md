## 結論

**Redis ZSET + 1本のLuaスクリプトによる sliding-window log**にします。キーは認証済み `user_id` 単位とし、全インスタンス・全workerが同じRedisを参照します。プロセス内辞書は使いません。

| 項目 | 設計 |
|---|---|
| キー | `rate:{user_id}` |
| 値 | ZSET。score=Redis時刻、member=サーバ側で生成したHTTP試行ID |
| 判定窓 | 直近60秒。境界を明確化し、**ちょうど60秒前も含む** `[T-60s, T]` とする |
| 上限 | 窓内100件まで許可。101件目は `429` |
| 原子性 | Lua内で削除→重複確認→件数確認→追加まで一括実行 |
| 時刻 | 各workerの時計ではなくLua内の `Redis TIME` を使用 |
| TTL | 最終許可から **61秒程度**。TTL自体は判定に使わず、不要キーの回収専用 |
| Redis障害 | **fail closed**。タイムアウト・接続失敗等は `503`、業務処理へ進めない |

Luaの処理は概念的に次の順です。

1. `Redis TIME` で `now` を取得。
2. `now - 60s` **より古い**要素だけ `ZREMRANGEBYSCORE` で削除。境界上の要素は残す。
3. 同じHTTP試行IDが既に存在すれば、Redis通信の再実行とみなし再加算せず「許可済み」を返す。
4. `ZCARD >= 100` なら追加せず `429`。
5. それ以外は `ZADD` し、TTLを約61秒へ更新して許可。

### リトライ

**利用者から届く新しいHTTPリトライは別1件として数えます。** 同じ業務操作だからという理由でクライアント指定のIdempotency-Keyをレート制限のmemberにすると、同じキーの使い回しで制限を迂回できるためです。

一方、RedisへのLua実行で「実行済みだが応答だけ失われた」場合の内部リトライは、**同じサーバ生成試行ID**を使います。これにより二重計上を防げます。結果不明のままRedisへ接続できなければ `503` とし、インメモリ制限へフォールバックしません。

### 確認テスト

1. **基本**: 同一userで100件は許可、同じ60秒窓の101件目は429。
2. **並行性**: 8 worker以上から同時に、空の同一userへ例えば200件投入し、許可が厳密に100件であること。
3. **インスタンス跨ぎ**: 2インスタンスへ分散しても合計100件までであること。
4. **user分離**: user Aが100件使用してもuser Bには影響しないこと。
5. **60秒境界**: 最古の要求からちょうど60.000秒時点ではまだ101件目を拒否し、境界を越えた直後に許可されること。
6. **同時期限切れ**: 多数の古い要素が窓外になる瞬間に並行要求を流しても100件を超えて許可されないこと。
7. **Redis内部リトライ**: Lua成功後の応答喪失を模擬し、同じ試行IDで再実行しても1件しか記録されないこと。
8. **HTTP再送**: 新しいHTTP試行IDなら別件として計上されること。
9. **TTL**: 最終許可から約61秒後にキーが消えること。TTL直前でも判定結果が変わらないこと。
10. **障害**: Redis停止・timeout・script error時に503となり、業務処理が実行されないこと。

### 次の方向

実装時には、Luaスクリプトの戻り値を `allowed / limit / retry_after` に固定し、429の `Retry-After` をZSET最古要素の時刻から計算すると運用しやすくなります。
