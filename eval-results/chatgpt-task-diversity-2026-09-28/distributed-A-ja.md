結論は、**共有Redisに `user_id` ごとのZSETを持ち、1回のLuaスクリプトで「60秒超の削除→件数確認→許可時だけ追加」を原子的に行う sliding log 方式**です。これが「任意の連続60秒で100件以下」を厳密に満たす最小構成です。固定窓・プロセス内辞書は要件を満たしません。

### 設計

キーは例えば `rl:v1:{user_id}`、ZSETの各要素を「許可したHTTP試行1件」とします。

Luaスクリプト内で次を一括実行します。

1. `TIME` でRedis自身の現在時刻を取得する。全インスタンスで同一時計を使い、APIサーバ間の時刻ずれを排除する。
2. `cutoff = now - 60秒` を計算する。
3. `ZREMRANGEBYSCORE key -inf cutoff` で、**ちょうど60秒以前**の記録を削除する。
4. `ZCARD key` を確認する。
5. 100件以上なら追加せず `429 Too Many Requests`。
6. 100件未満なら、今回の試行を一意なmemberで `ZADD` して許可する。
7. 許可した場合、キーに例えば **61秒程度のTTL** を設定し直す。

したがって対象窓は `(now - 60s, now]` です。ちょうど60秒前の要求は窓外になります。固定窓のように「59.9秒に100件、60.1秒にさらに100件」が通ることはありません。

LuaはRedis上で原子的に実行されるため、4 worker × 2インスタンスから同時に到着しても、

> 削除 → 件数判定 → 追加

の途中に別要求が割り込まず、同じユーザーについて101件目が同時に許可される競合を防げます。

ZSET memberには各**HTTP試行ごとのランダムUUID等**を使います。同一時刻に複数件来てもmemberが衝突しません。時刻は可能ならRedis `TIME` のマイクロ秒まで利用します。

### リトライ

最小で明確な規則は、**リトライも別のHTTP試行として数える**ことです。

- 許可済み要求が通信断などで再送された場合 → 再送分も1件として数える。
- 429で拒否した要求 → ZSETには追加しない。
- その要求を後から再試行して許可された場合 → その時点で1件として追加する。
- アプリ処理が500等で失敗しても、レート制限を通過済みなら取り消さない。

これにより、業務処理の成功・失敗とレート制限を分離できます。同じIdempotency-Keyの再送を「1件」と扱いたい場合は、それは別途idempotency機構として実装するのが適切です。ユーザー指定のIdempotency-KeyをZSET memberにそのまま使うと、同じキーを使い回して制限を回避できるため避けます。

429時には最古の有効要素のtimestampから、

`oldest + 60秒 - now`

を算出して `Retry-After` の基礎値として返せます。

### キー寿命

TTLは**最後に許可した要求から61秒程度**で十分です。60秒を少し超えさせるのは、まだ有効な記録がTTLで先に消えることを避けるためです。

古い要素は毎回のLua実行で削除するため、TTLを61秒にしても判定窓が61秒になるわけではありません。TTLは純粋に未使用ユーザーのメモリ回収用です。

拒否のたびにTTLを延長する必要はありません。攻撃者が429を送り続けるだけでキーが永久に残るのを避けられます。

### Redis障害

要求どおり **fail closed** とします。

- Redis接続不能
- Redisタイムアウト
- Lua実行失敗
- 判定結果を確定できない状態

はいずれも **503 Service Unavailable** とし、ローカル辞書等へフォールバックしません。ローカルフォールバックすると全インスタンス合算の100件制限を保証できなくなるためです。

一点だけ、厳密性を障害復旧後まで要求するなら注意が必要です。**Redis再起動で直前60秒のZSETが失われた状態で即座に受付再開すると、100件制限を破る可能性があります。**したがってデータ喪失が起こり得る構成なら、少なくとも次のどちらかが必要です。

- rate-limit状態を失わないRedis運用にする。
- 状態喪失を検知したRedisについて、復旧後60秒間は503としてから受付を再開する。

また、厳密制限が必要なRedisではrate-limitキーが任意にevictionされない構成にします。

### 確認テスト

| テスト | 条件 | 期待結果 |
|---|---|---|
| 基本上限 | 同一userに60秒以内で101件 | 100件だけ許可、101件目は429 |
| 並行更新 | 8 workerへ同一userの200件を同時投入 | **合計ちょうど100件以下**だけ許可 |
| ユーザー分離 | user A/Bに各100件 | 双方100件ずつ許可 |
| 60秒境界 | t=0付近で100件、その後t<60秒 | 追加要求は429 |
| 境界直後 | 最古要求からちょうど60秒経過 | その要求が窓外になり、新規要求を許可 |
| 固定窓対策 | ある秒境界直前に100件、直後に追加 | 最初の要求が60秒経過するまでは429 |
| リトライ | 許可済み要求を再送 | 別試行として追加カウント |
| 拒否の再試行 | 101件目を429、その後古い1件が窓外になって再試行 | 最初の429では増えず、再試行時に許可・追加 |
| TTL | 最後の許可後、61秒超アクセスなし | キー消滅 |
| Redis停止 | Redisを停止して要求 | 全インスタンスで503、要求を通さない |
| Redis復旧・状態喪失 | データ消失を伴う再起動 | 安全な60秒経過まで503、または永続状態から復旧 |

実装上の中心はLuaスクリプト1本だけで、**追加の分散ロックやプロセス内キャッシュは不要**です。
