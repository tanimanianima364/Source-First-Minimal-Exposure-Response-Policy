# 本番集計切替 決裁メモ

**決裁対象:** proposed-plan r1  
**希望切替日:** 2026年10月5日（月）  
**判断基準:** 03:00までの確定成果物1件の公開、重複・欠落防止、再実行可能性、30日監査、アクセス制御、既存環境・12時間の開発枠内での実現性

## 1. 決裁結論

**proposed-plan r1 は否決する。**

主因は、10月5日時点では本番v3が利用できないこと、v2ではr1が前提とする25 MB上限および冪等再送が成立しないこと、さらに「成功ログを先に記録してから共有成果物を上書きする」手順が停止時に欠落を発生させ得ることである。

代替として、**Export APIを使用せず、既存Windowsサーバー上でPythonにより部署別合計をローカル計算し、検証済み成果物だけを共有フォルダへ公開する構成**を推奨する。追加SaaS・新規サーバー・v3有効化を必要とせず、現時点で最も実行可能性が高い最小構成である。

ただし、**10月5日切替は条件付き**とする。後記のリリース前合否条件をすべて満たせない場合は切替を行わない。

## 3. 現行案 r1 の重大な問題

### 3.1 10月5日にv3を前提とすることが成立しない

v3の本番有効化日は**10月8日**であり、希望切替日の**10月5日**より後である。したがって、r1の「10月5日にv3の25 MB仕様を前提に切り替える」は日程上成立しない。

10月5日時点のv2は1ジョブ10 MB上限であるため、18 MB入力でも最低2分割、24 MBでは最低3分割が必要になる。またv2には冪等キーがなく、POSTタイムアウト後の再送で別ジョブが作られ得る。

よってr1の「同じ内容を再送すれば重複しない」という前提は、10月5日時点の本番環境には適用できない。

### 3.2 v2経路は工数上も不適合

v2経路の開発見積りは**20時間**であり、利用可能な**12時間**を既に超える。さらに20時間には復元試験・障害試験が含まれていない。

したがって、分割ジョブ、再送、全分割結果の完全性確認、合算までを10月5日に新規実装する案は、現条件では採用しない。

### 3.3 「成功ログを先に書く」順序は欠落を生む

r1では、

1. 成功ログを書く  
2. 共有成果物を上書きする  
3. 再実行時、日付が成功ログにあれば処理を飛ばす

としている。

成功ログ記録後、共有への公開前にプロセス停止・OS停止等が発生すると、**成果物が存在しないにもかかわらず再実行がスキップされる**。これは「欠落不可」に直接反する。

成功判定はログの存在ではなく、**共有上の最終成果物が存在し、期待するハッシュ等で検証できたこと**を根拠にしなければならない。

### 3.4 共有フォルダへの上書き安全性は未確認

共有フォルダについて、

- 既存成果物の置換が他プロセスから一括で見えるか
- 電源断後に期待する状態が永続するか

は未検証である。

ローカルNTFSで観測した置換動作を共有フォルダに一般化してはならないため、既存ファイルを直接上書きする設計を前提に本番投入してはならない。

### 3.5 試験と切戻し計画が不足

正常系1件だけの試験では、今回重要な「停止・再実行時に重複・欠落しないこと」を確認できない。

また、ロールバック担当を切替後に決める案は不適切である。切替前に責任者、判断条件、旧状態へ戻す手順を確定させる必要がある。

## 4. 推奨する最小構成

### 構成

- Windowsタスクスケジューラから毎日02:00にPythonを起動する。
- 入力をローカルの制限済みNTFS作業フォルダで読み取る。
- `対象日 + 入力sha256` を**実行ID**とする。
- Pythonで部署別合計を計算する。
- 成果物をまずローカル作業フォルダに完成させる。
- 件数・集計結果・成果物sha256等を検証後、共有フォルダへ公開する。
- 同一対象日の最終成果物は1件だけとし、正常な再実行では2件目を作成しない。
- 実行ID、開始・終了、入力sha256、成果物sha256、処理件数、状態遷移、エラー、再実行結果を監査記録として30日保持する。

Export API v2/v3は使用しない。

### 公開ファイルの扱い

共有上の最終ファイル名は対象日で一意にする。例:

`result_2026-10-02.csv`

共有へ直接この名前で書き始めず、まず同一共有フォルダ内の一時名へコピーする。

例:

`._result_2026-10-02_<実行ID>.tmp`

コピー完了後にサイズ・sha256を確認し、一時名から最終名へ切り替える。

**既存の正常な最終ファイルは原則として上書きしない。**

再実行時に最終ファイルが既に存在する場合は、

- 期待する成果物sha256と一致 → 既に公開済みとして正常終了
- 不一致 → 自動上書きせず異常終了し、担当者判断へ送る

とする。

これにより、再実行のたびに成果物を増やしたり、正常成果物を誤って置換したりする経路を排除する。

共有フォルダ内での「一時名から未存在の最終名への変更」が読者から部分ファイルとして見えないことについては、**本番前試験で確認することをリリース条件とする**。共有ストレージの動作は現時点では保証済みではない。

## 5. 停止・再実行時の重複・欠落防止

処理状態は次の事実から復元できるようにする。

1. 対象日と入力sha256
2. ローカルに完成済み成果物があるか
3. その成果物sha256
4. 共有上の最終成果物が存在するか
5. 共有成果物sha256が期待値と一致するか

単なる「成功ログあり」を完了条件にしない。

### 停止位置別の再実行

| 停止位置 | 再実行時の扱い |
|---|---|
| 入力読込・集計途中 | 同じ対象日＋sha256で最初から再計算する |
| ローカル成果物作成途中 | 未完成物を破棄し再作成する |
| ローカル成果物完成後、共有コピー前 | 完成済み成果物を再検証して共有公開を再試行する |
| 共有一時ファイルコピー途中 | 不完全な一時ファイルを削除または隔離し、再コピーする |
| 共有への公開直後、成功記録前 | 共有の最終成果物をsha256確認し、一致すれば公開済みとして記録を補完する |
| 成功記録後 | 最終成果物が存在しsha256一致することを再確認して正常終了する |
| 同一日の最終成果物が存在するがsha256不一致 | 自動置換せず異常停止する |

タスクの多重起動も避ける。タスクスケジューラを「既存インスタンス実行中なら新規起動しない」設定とし、加えて実行ID単位の排他をローカル側で行う。

この方式では、**ログを正とせず実物とハッシュを正とする**ため、公開前後で停止しても再実行による欠落・二重公開を防止できる。

## 6. 監査記録

最低限、次を30日保存する。

- 対象日
- 実行ID
- 入力ファイル名
- 入力サイズ
- 入力sha256
- 開始日時・終了日時
- 入力行数または処理レコード数
- 出力部署数等の完全性確認値
- ローカル成果物sha256
- 共有成果物sha256
- 公開ファイル名
- 各処理状態と日時
- 再実行回数
- エラー内容
- 最終結果

監査ログは既存のアクセス制限済みローカル作業領域に保存する。

## 7. リリース前の合否条件

以下を**すべてPassした場合のみ**10月5日に切り替える。

### 必須機能

1. 24 MB相当入力を02:00相当条件で処理し、03:00以前に検証済み成果物を1件だけ公開できる。
2. 入力sha256が同じ再実行で二重成果物を作らない。
3. 異なる入力sha256を同じ対象日として検出した場合、自動的に既存成果物を置換しない。
4. 監査情報を30日保持できる。
5. 実行アカウント・担当者以外が入力を読めない既存ACLが維持される。

### 障害・再実行試験

少なくとも以下を実施する。

- 集計途中で強制終了 → 再実行で正常完了
- ローカル成果物完成後に強制終了 → 再実行で正常公開
- 共有への一時コピー途中で停止 → 部分ファイルを最終成果物として扱わず復旧
- 共有公開直後、成功記録前で停止 → 再実行で既存成果物を検証し二重公開しない
- 完了後の再実行 → 成果物を増やさず正常終了
- 共有最終成果物を意図的に不一致状態にした試験 → 自動上書きせず停止

### 共有フォルダ試験

現在未確認のため、以下をGo/No-Go判定項目とする。

- 一時ファイルから最終ファイル名への切替中に、同時読者が部分成果物を最終成果物として取得しないこと
- 停止・再起動後、公開済みと判断するファイルの存在およびsha256を再検証できること

この挙動が確認できない場合、10月5日の本番切替はNo-Goとする。

## 8. 性能と工数の判断

既存測定では、24 MB相当サンプルについて、

- Python処理: 42秒
- タスク開始から共有コピー完了: 110秒

であり、03:00期限に対して測定上は十分な余裕がある。

ただしこれは**1サンプルだけの実績**であり、月末実データ、同時読者、停止・再実行については未検証である。そのため「性能要件を保証済み」とは扱わない。

工数はローカルPython経路が**8時間**、利用可能時間が**12時間**であり、名目上は4時間の差がある。

一方、この8時間には復元試験・障害試験が含まれていない。したがって、**現時点では必要作業全体が12時間以内に収まることは保証できない。**

10月5日の切替可否は、実装時間だけでなく上記障害試験・切戻し確認まで12時間の実作業枠内で完了できることを条件とする。時間切れを理由に試験項目を削って切り替えてはならない。

## 9. 切戻し責任と手順

### 責任

2名の担当者について、切替前に必ず以下を実名で指定する。

- **切替・切戻し責任者:** Go/No-Goおよび切戻しを決定する1名
- **確認担当:** 成果物、ログ、旧状態復帰を確認する1名

「切替後に担当を決める」ことは禁止する。

### 事前準備

切替前に、

- 既存の本番タスク・設定・実行手順を変更前の状態で保存する
- 新規タスクを単独で無効化できることを確認する
- 新方式が公開するファイル・作業ディレクトリ・ログを明確に分離する
- 現行運用へ戻す具体的な操作手順を記録する

とする。

現行バックアップは最終復元試験が未実施であるため、**バックアップからの復元を唯一の切戻し手段にしてはならない。** バックアップ復元を切戻し手順に含める場合は、事前に復元試験をPassさせる。

### 切戻し条件

次のいずれかが発生した場合は、新方式を停止する。

- 03:00までに正常成果物を1件確定できない
- 入力または成果物の完全性を確認できない
- 二重公開または欠落の可能性を排除できない
- 共有成果物sha256が期待値と一致しない
- 監査記録を正常に残せない
- アクセス制御に逸脱がある

### 切戻し操作

1. 新規タスクを無効化し、再起動を防止する。
2. 共有上の成果物を検証し、不完全または未検証の成果物を正式成果物として扱わない。
3. 切替前に保存した旧タスク・設定・運用へ戻す。
4. 旧方式が正常に動作することを確認する。
5. 切戻し時刻、原因、共有上の最終状態、対象日、入力sha256を監査記録に残す。
6. 新方式を再開する場合は、障害原因の修正後に該当する障害試験を再度Passさせる。
