# 本番切替 決裁メモ

**対象:** proposed-plan r1  
**希望切替日:** 2026年10月5日（月）  
**決裁案:** **原案は不採用。v3/API依存を外し、既存Windowsサーバー上のローカルPython集計に差し替えて条件付き採用する。**  
ただし、下記のリリース前合否条件をすべて満たせない場合は10月5日の切替を延期する。試験を省略して日程を優先する判断はしない。

## 1. 判断理由

原案には、本番切替を成立させない重大な問題がある。

| 論点 | 確認済みの事実 | 判断 |
|---|---|---|
| v3利用日 | 本番テナントのv3有効化確定日は**2026-10-08**。前倒し未承認（Document T） | **10/5切替ではv3を前提にできない** |
| v2容量 | 1ジョブ10 MB上限。通常18 MB、月末最大24 MB（Documents V2/R） | 通常でも最低2ジョブ、24 MBでは最低3ジョブに分割が必要 |
| v2再実行 | v2に冪等キーなし。POST再送で別ジョブを作り得る。完全な成果物を揃える責任は呼出側（V2） | タイムアウト時の単純再送では重複・欠落防止を保証できない |
| 工数 | v2経路20時間、ローカルPython経路8時間。開発可能時間は合計12時間。障害・復元試験は見積り外（M/R） | v2は試験以前に工数超過。Python経路のみ現実的余地がある |
| API必要性 | 部署別合計はPython標準ライブラリ `csv`・`decimal` で処理可能。API利用は業務要件ではない（M） | APIを使う理由がなく、依存を増やすべきでない |
| 性能 | 24 MB相当サンプルで処理42秒、タスク開始から共有コピー完了まで110秒。ただし1サンプルのみ（M） | 03:00期限には十分な余裕が見込まれるが、**月末実データ・同時読者・停止試験は未確認** |
| 原案の成功判定 | 成功ログを書いてから共有成果物を上書きし、日付の成功ログがあれば再実行を飛ばす（P） | ログ記録後・公開前に停止すると「成功扱いだが成果物なし」になり得る。欠落を固定化する |
| 共有フォルダ | 既存成果物置換の一括可視性、電源断後の永続性が未検証。ローカルNTFSの性質を一般化不可（T） | 原案の「共有上書き」を安全とみなせない |
| 切戻し | 原案では切替後に担当を決める（P） | 本番移行条件として不適格 |

したがって、**proposed-plan r1のままの採用は不可**とする。

## 2. 推奨する最小構成

追加SaaS、Export API、追加サーバーは使用しない。

**構成**
- 既存Windowsサーバー1台
- Windowsタスクスケジューラ
- 承認済みPython標準ライブラリのみ
- 制限済みローカルNTFS作業フォルダ
- 既存共有フォルダ
- 実行アカウント＋担当者2名

タスクは毎日02:00に起動する。タスクスケジューラ側で多重起動を禁止し、Python側でもプロセスロックを取る。

入力はローカル制限フォルダからのみ読む。共有フォルダへ置くのは集計済み成果物だけとし、入力CSVそのものや入力内容を含むデバッグファイルは置かない。

## 3. 入力完全性と実行識別

「存在したCSVを全部処理する」だけでは、ある部署のCSV自体が届かなかった場合を検出できない。したがって、本番前に**期待部署一覧または日次到着マニフェスト**を確定することを必須とする。

処理開始前に次を検証する。

1. 対象日が前営業日であること
2. 期待する全部署についてCSVが1件ずつ存在すること
3. 同一部署の重複ファイル、想定外ファイルがないこと
4. 各CSVの形式、必須列、数値形式が妥当であること

複数CSVについて、部署ID・ファイル名・サイズ・各ファイルのSHA-256を正規化した一覧を作り、その一覧のSHA-256を**日次入力集合のハッシュ**とする。

**実行ID = 対象業務日 + 日次入力集合SHA-256**

とする。

同一日・同一SHA-256なら同一処理として扱う。同一日について異なるSHA-256が現れた場合は、入力は到着後不変という前提との矛盾なので、**自動上書きせず異常終了**する。

なお、資料から保証できるのは「ファイルを処理系が重複・欠落させないこと」である。CSV内部に元から重複レコードがあるかを業務的に判定するキーは提示されていない。元データ内のレコード重複検知まで要件に含むなら、レコード一意キーの定義を追加する必要がある。

## 4. 停止・再実行でも重複・欠落させない処理

処理順序は以下とする。

1. 入力完全性を確認し、実行IDを確定する。
2. 全CSVをローカルで一度ずつ読み、`decimal` で部署別合計を計算する。
3. ローカル一時ファイルへ成果物を書き、クローズ後にSHA-256を計算する。
4. ローカル上で「完成済み成果物」として確定する。
5. 共有フォルダには、最終ファイル名とは異なる**一時名**で完成済み成果物だけをコピーする。
6. コピー後の共有一時ファイルを再読込し、ローカル成果物とSHA-256が一致することを確認する。
7. 同じ共有ディレクトリ内で、一時名から日付固定の最終名へ変更する。  
   例: `2026-10-02.csv`
8. 最終ファイルを再読込し、SHA-256一致を確認する。
9. **ここで初めて成功記録を永続化する。**

最終名のファイルは原則として上書きしない。既に存在する場合は、
- SHA-256が今回期待値と同一 → 既に公開済みとして成功扱い
- SHA-256が異なる → 自動上書きを禁止して異常終了

とする。

これにより停止位置ごとの動作は次のとおりになる。

- **共有コピー途中で停止:** 最終名は存在せず、一時ファイルだけが残る。再実行で作り直せる。
- **最終名への変更直前に停止:** 同上。
- **最終名への変更後、成功ログ前に停止:** 再実行時に最終ファイルのSHA-256を照合し、同一なら再公開せず成功記録だけ補完する。
- **成功ログ後に電源断し共有成果物が失われた場合:** 成功ログだけで処理を飛ばしてはならない。毎回、最終ファイルの存在とSHA-256を再確認し、欠けていれば同じ実行IDから再生成・再公開する。

したがって、**「日付の成功ログがあるからスキップ」という原案の判定は禁止**する。

監査ログには最低限、対象日、実行ID、各入力SHA-256・サイズ、入力件数、開始・終了時刻、出力SHA-256、最終パス、各状態遷移、エラー、再実行履歴を記録し、制限済みローカルフォルダに**30日以上**保持する。

## 5. 共有フォルダについて未保証の点

上記方式は「既存成果物の上書き」を避けるため、原案より安全性が高い。ただしDocument Tのとおり、共有フォルダについて次は未確認である。

- 一時名から最終名への変更中、同時読者から部分的な最終ファイルが見えないこと
- 電源断後に最終ファイルが残ること
- 電源断後に失われても、再起動時の照合・再実行で一意な成果物へ復旧できること

これらはローカルNTFSの挙動から推定して合格扱いにしてはならず、実際の共有フォルダで試験する。

## 6. リリース前の合否条件

**全項目合格を10月5日切替の条件**とする。日程上は、遅くとも**10月2日（金）の業務終了までにGo/No-Goを確定**する運用を推奨する。

### 機能・正確性
- 期待部署一覧または到着マニフェストが確定している。
- 前営業日の決め方が明文化されている。
- 正常データについて既知の正解値と一致する。
- CSV欠落、部署重複、形式不正、数値不正では成果物を公開しない。
- 24 MB相当データを処理できる。

### 再実行・障害
少なくとも以下の位置でプロセスを強制停止し、再実行する。

- 集計中
- ローカル成果物確定後
- 共有への一時コピー中
- 共有一時ファイル検証後
- 最終名への変更直後・成功ログ前
- 成功ログ後

すべてについて、最終的に**対象日につき最終成果物が1つだけ存在し、SHA-256が期待値に一致すること**を確認する。

二重起動試験も行い、同じ日次処理が並行実行されないことを確認する。

### 共有フォルダ
同時にファイルを読むプロセスを動かしながら公開し、
- 読者が部分的な最終成果物を正常成果物として取得しない
- 最終名が複数作られない
- 公開後のSHA-256が変化しない

ことを確認する。

### 電源断・再起動
少なくとも一度、公開前後の異常停止または強制再起動を含む試験を実施し、再起動後の照合・再実行で成果物が一意に復旧することを確認する。

タスクスケジューラには、起動時刻を逃した場合の再実行設定も入れる。

### 性能
現状の110秒という測定値だけでは合格としない。24 MB相当＋同時読者条件で測定する。

運用余裕を確保するため、**1回の処理を10分以内**、入力完全性の運用上の締切を**02:30以前**とすることを推奨する。これなら単発障害からの再実行時間を03:00まで確保できる。

ただし、入力が何時までに全部到着するかは資料に記載がない。上流から02:30までの完全到着を保証できない場合、03:00公開を処理系だけで保証することはできない。

### 権限
- 入力作業フォルダを実行アカウントと担当者だけが読めることを実アカウントで確認する。
- 共有には集計結果だけが出ることを確認する。
- ログに入力データ本文を残さない。

### 監査・復元
- 30日未満のログを自動削除しない設定を確認する。
- 現行バックアップを監査記録保全に依存するなら、最低1回の復元試験を行う。

Document Tでは現行バックアップの最終復元試験が未実施であるため、復元試験を行わない場合は「記憶媒体障害後も30日監査記録を回復できること」は未保証として残る。

## 7. 工数判断

確認済みの見積りは、
- ローカルPython実装: **8時間**
- 利用可能時間: **12時間**
- 残余: **4時間**

である。

ただし8時間には障害試験・復元試験が含まれていない。このため、**「12時間内に実装と全合否試験まで必ず完了できる」とは現在の資料から保証できない。**

推奨方針は、実装を8時間程度で完了させ、残り時間を障害・共有・復元・切戻し試験へ優先配分すること。4時間で必須試験を終えられない場合、試験を削るのではなく切替を延期する。

v2経路は20時間見積りであり、この判断対象から除外する。v3は10月8日まで本番利用できないため、10月5日の代替案にならない。

## 8. 切戻し責任と手順

切替前に、担当者2名について次の役割を**氏名で確定**する。

- **リリース／切戻し責任者:** タスク有効化・停止、切戻し判断、復旧操作を実施
- **検証担当者:** 入出力SHA-256、最終成果物一意性、監査ログを独立確認

「切替後に決める」は不可とする。

切戻し条件は、少なくとも以下とする。

- 最終成果物のSHA-256不一致
- 同一日で異なる入力SHA-256を検出
- 共有フォルダの公開一意性試験に反する挙動
- 再実行後も一意な成果物へ収束しない
- 03:00期限を守れない見込みになった
- 入力完全性を確認できない

**切戻し手順**
1. 新しいタスクスケジューラジョブを無効化し、実行中プロセスを停止する。
2. 入力、作業ファイル、監査ログを削除せず保全する。
3. 共有の最終成果物が期待SHA-256と一致する場合は、その正しい成果物を不用意に消さない。
4. SHA-256不一致または状態不明の成果物を「成功」と扱わず、インシデントとして隔離する。
5. 切替前の承認済み運用へ戻す。
6. 旧運用で生成した成果物も対象日・内容を照合し、共有上で有効な最終成果物を1つにする。
7. 切戻し理由、時刻、担当者、成果物SHA-256を監査記録に残す。

ただし、**資料には「切替前の現行運用」の具体的な手順が記載されていない。** 手動表計算は無人実行要件を満たさないため、それだけを恒久的な切戻し先とはみなせない。

したがってリリース前に、旧運用の実行手順、必要資格情報、所要時間、03:00期限への影響をRunbookに記載し、担当者2名で一度切戻し訓練を実施することを合格条件とする。旧運用が03:00無人公開を満たさない場合は、その制約を明示した上で、緊急時の一時的例外を誰が承認するかも事前に決める。

## 9. 現時点で確認済みのこと／まだ保証できないこと

**確認済み**
- 10月5日にv3は利用できない。
- v2は10 MB制限かつ冪等性なし。
- v2実装20時間は12時間枠を超える。
- Python標準ライブラリだけで要求された部署別合計を計算できる。
- 24 MB相当サンプルは42秒、共有コピー完了まで110秒だった。
- 入力作業フォルダのアクセス制限は既に設定済み。
- 高可用性、多拠点構成、追加SaaSは要求されていない。

**リリース前試験なしには保証できない**
- 全部署ファイルの到着完全性
- 月末実データでの性能
- 同時読者がいる共有フォルダでの公開一意性
- 強制停止・再実行後の収束
- 電源断後の共有成果物の永続性
- 現行バックアップからの復元
- 12時間枠内で必須障害試験まで完了できること
- 切替前運用への実効的な切戻し
- 上流入力が03:00公開に間に合う時刻までに揃うこと

## 最終決裁

**proposed-plan r1: 不採用。**

**代替案: 既存Windowsサーバー＋タスクスケジューラ＋ローカルPythonによる単一日次集計を条件付き採用。**

10月5日に切り替えるためのGo条件は、上記の入力完全性、停止・再実行、共有公開、電源断、性能、権限、監査、切戻しの試験をすべて完了し、担当者2名が結果を確認していることである。

一つでも未合格なら、10月5日の切替を延期する。特に、未検証の共有フォルダ挙動を「NTFSだから安全」と仮定すること、成功ログだけを根拠に再実行を省略すること、試験を省いて12時間枠へ収めることは認めない。

根拠は、rollout-requirements r4、Export API v2/v3 manual、tenant-readiness 2026-09-27、options-and-measurements r2、proposed-plan r1 の記載だけを使用しています。
