## 最小構成

必要なのは次の3要素です。既存製品だけで構成し、表計算ソフトは本番処理経路から外します。

| 要素 | 用途 |
|---|---|
| 承認済み自動化ランナー上の集計ジョブ1本 | 日次起動、CSV検証、部署別集計、出力、再実行制御 |
| 既存共有フォルダーの権限分離された領域 | 入力受け渡し、処理中ファイル、最終出力、完了情報の保存 |
| ランナーの実行ログ | 実行履歴、件数、結果、エラーの保持 |

インストール済み表計算ソフトは、無人実行、耐障害性、継続的なログ保持に対応していないため、本番ジョブには使用しません。ただし、テスト時の独立した検算には利用できます。

### 構成イメージ

```text
入力担当者
   │ CSV配置、準備完了通知
   ▼
共有フォルダー /landing
   │
   ▼
承認済み自動化ランナー
   ├─ 入力の固定・ハッシュ計算
   ├─ CSV形式検証
   ├─ 部署別集計
   ├─ 一時領域への出力
   ├─ 整合性検査
   └─ 最終領域へ一括公開
   │
   ▼
共有フォルダー /output/YYYY-MM-DD/
   ├─ department_totals.csv
   └─ manifest
```

共有フォルダー内には、少なくとも次の論理領域を設けます。

| 領域 | 主な権限 |
|---|---|
| `/landing` | 入力担当者は書き込み、ランナーは読み取り・移動 |
| `/staging` | ランナー専用。利用者はアクセス不可 |
| `/output` | ランナーは作成、結果利用者は読み取り専用 |
| `/archive` または `/state` | ランナーと運用管理者のみ |

ランナーは専用サービスアカウントで動作させ、共有フォルダーの権限変更権限は付与しません。

## 重複書き込み防止

「実行を必ず1回だけにする」のではなく、ジョブは再実行され得る前提で、**同じ処理対象を最終成果物として1回だけ公開する**方式にします。

### 1. 処理キー

毎日の処理であるため、基本の処理キーを業務日付とします。

```text
job_key = 対象業務日 YYYY-MM-DD
```

入力CSVの内容からハッシュ値も計算し、完了情報に保存します。これにより、ファイル名だけ変更された同一入力と、同じ日付だが内容が変更された入力を区別できます。

### 2. 出力は追記しない

累積CSVへの追記は禁止します。毎日、次の固定された最終パスへ、その日の完全な集計結果を公開します。

```text
/output/YYYY-MM-DD/department_totals.csv
```

出力は部署ごとに1行を持つCSVとするのが最小構成です。部署別に複数ファイルが必要な場合も、同じ日付ディレクトリ内にまとめて一括公開します。

### 3. 一時出力から一括公開

ジョブは直接最終パスへ書きません。

1. 実行ごとに一意な一時ディレクトリを作る  
2. CSVと完了情報を一時ディレクトリ内に書く  
3. 件数、合計値、出力ハッシュを検査する  
4. ディレクトリ全体を最終パスへ、上書き不可で原子的に公開する  

完了情報には少なくとも次を記録します。

- 処理キー
- 入力ファイル名と入力ハッシュ
- 入力行数、正常行数、エラー行数
- 部署数
- 出力ファイル名と出力ハッシュ
- 実行ID
- 開始・終了日時
- ジョブ定義の版
- 完了状態

### 4. 再実行時の判定

| 状態 | 動作 |
|---|---|
| 最終出力がなく、一時出力だけがある | 一時出力を完成品とは扱わず、再集計する |
| 最終出力があり、入力ハッシュも一致 | 書き込みを行わず「処理済み」として正常終了 |
| 最終出力があり、入力ハッシュが異なる | 自動上書きせず、入力競合として異常終了 |
| 別の実行が同時に最終公開した | 公開処理は失敗させ、既存結果を検査して一致すれば処理済み終了 |
| 公開後、成功ログ記録前に停止した | 次回は既存の最終出力を検査し、再書き込みせず終了 |

同一日付で入力内容を差し替える必要がある場合は、通常の再実行とは分離し、運用管理者による明示的な訂正処理にします。自動的な上書きを許すと、誤入力や二重処理を検知できなくなります。

## 実行ログ

ランナーが保持するログには、少なくとも次を出力します。入力CSVの明細値そのものは記録しません。

- 実行ID、処理キー
- スケジュール起動か手動再実行か
- 入力パス、入力ハッシュ
- 入力行数、正常・エラー行数
- 部署数、集計総額などの照合値
- 出力パス、出力ハッシュ
- `SUCCESS`、`ALREADY_COMPLETED`、`INPUT_CONFLICT`、`VALIDATION_ERROR`などの終了状態
- エラー内容と失敗した処理段階

ログ保持期間は組織の規定に合わせてランナー側で設定します。共有フォルダー上の完了情報は、ランナーのログとは別の再実行判定用データです。

## アクセス制御

最小権限は次のようにします。

| 役割 | 入力領域 | 一時・状態領域 | 出力領域 | 実行ログ |
|---|---:|---:|---:|---:|
| 入力担当者 | 書き込み | 不可 | 不可または不要 | 不可 |
| ランナー用サービスアカウント | 読み取り・移動 | 読み書き | 作成・読み取り | 書き込み |
| 結果利用者 | 不可 | 不可 | 読み取りのみ | 不可 |
| 運用担当者 | 必要に応じ読み取り | 読み取り | 読み取り | 読み取り、再実行 |
| 権限管理者 | 権限管理 | 権限管理 | 権限管理 | 管理方針に従う |

入力中のファイルを処理しないよう、入力担当者は一時名でアップロードし、完了後に名称変更するか、別の準備完了ファイルを配置します。ランナーは準備完了が確認できたファイルだけを処理対象にします。

## 検証方法

### 1. 集計の正確性

既知の期待値を持つテストCSVを作り、次を確認します。

- 各部署の件数と集計値が期待値と一致する
- 出力に同じ部署が複数行現れない
- 全部署の合計が、入力全体の対象列合計と一致する
- 入力行数が「正常行数＋エラー行数」と一致する
- 空欄、未知部署、不正数値、重複ヘッダーなどの扱いが仕様どおりである

表計算ソフトで同じテストCSVを手動集計し、ランナーの結果と比較すれば、独立した検算になります。

### 2. 5万行の容量検証

本番相当の5万行CSVで次を確認します。

- 途中で行が欠落または切り捨てられない
- 集計値と件数が照合できる
- 割り当てられた日次処理時間内に終了する
- ログに入力件数、部署数、出力件数が記録される
- メモリ不足や一時ファイル容量不足が発生しない

### 3. 無人定時実行

利用者がログインしていない状態で入力を配置し、次を確認します。

- 指定時刻にジョブが起動する
- 出力とログが生成される
- 対話操作や表計算ソフトの画面操作を要求しない
- 入力がない場合の状態が明確に記録される

### 4. 通常の再実行

同じ入力、同じ業務日付で2回実行します。

合格条件は次のとおりです。

- 最終出力ディレクトリは1つだけ
- 出力CSVのハッシュが変化しない
- 2回目は出力ファイルを変更しない
- 2回目のログが `ALREADY_COMPLETED` になる
- 出力行や合計値が二重にならない

可能であれば、最終出力の更新日時も2回目に変化しないことを確認します。

### 5. 障害注入と再実行

次の各地点で意図的に処理を停止し、その後再実行します。

| 停止地点 | 期待結果 |
|---|---|
| 入力読込前 | 最終出力なし。再実行で正常生成 |
| 入力読込中 | 最終出力なし。再実行で正常生成 |
| 一時CSV書込中 | 不完全ファイルは一時領域だけに残り、公開されない |
| 集計完了後、公開前 | 再実行で有効な結果を1回だけ公開 |
| 最終公開直後、成功ログ前 | 再実行は既存結果を検出し、再書き込みしない |
| 完了後 | 再実行は処理済み終了 |

どの試験でも、最終領域には「有効な完全版が1つ」または「何もない」のどちらかしか存在しないことを確認します。

### 6. 同時実行

同じ業務日付のジョブを意図的に2本同時起動します。

合格条件は次のとおりです。

- 片方だけが最終公開に成功する
- もう片方は既存結果を検査して処理済み終了する
- 最終出力は1組だけ
- 部分ファイルや重複出力が最終領域に残らない

### 7. 入力差し替え

同じ日付で内容が異なるCSVを再投入します。

合格条件は、自動上書きや第2の成果物作成ではなく、入力ハッシュ不一致として処理を停止し、ログに `INPUT_CONFLICT` を残すことです。

### 8. ログ保持

- 成功、処理済み、入力不正、処理失敗の各ログが検索できる
- ランナーを再起動しても過去ログが残る
- 設定した保持期間内のログが削除されない
- 実行IDから入力ハッシュと出力ハッシュを追跡できる

### 9. 権限試験

各役割のアカウントで、許可操作と拒否操作を実際に試します。

- 入力担当者が出力を変更できない
- 結果利用者が入力や一時領域を閲覧できない
- 結果利用者が出力を削除・更新できない
- ランナーだけが一時領域と最終出力を作成できる
- ランナーが共有フォルダーのアクセス権を変更できない

## 重要な受け入れ条件

提示されたケースでは、共有フォルダーについて明示されているのはロールベースのアクセス制御だけで、**「既存パスを上書きしない原子的な作成または名称変更」**が保証されているとは記載されていません。

したがって、本構成を正式に合格とする前に、同じ最終パスへの同時公開試験を行い、次のいずれかを実証する必要があります。

- 共有フォルダーが、上書き不可の原子的なファイルまたはディレクトリ公開を提供する
- ランナーが同一処理キーの同時実行を確実に排除し、かつ再実行前の完了判定が行える

どちらも実証できない場合、定時実行、ログ保持、アクセス制限、順次再実行時の冪等性までは実現できますが、同時再実行を含む強い重複書き込み防止は、提示された機能だけでは保証できません。これは追加製品の問題ではなく、既存共有フォルダーまたはランナーの排他・原子性を受入試験で確認すべきポイントです。
