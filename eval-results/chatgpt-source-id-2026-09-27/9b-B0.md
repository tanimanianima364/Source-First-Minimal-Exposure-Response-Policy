## 結論

要件を満たす最小の実行時構成は、次の3要素です。

1. **既存の自動化ランナー**：日次スケジュールと実行ログ保持  
2. **1本の集計ジョブ**：CSV集計、検証、再実行時の冪等制御  
3. **既存の共有フォルダー**：入力・作業・公開領域とRBAC

既存の表計算ソフトは、利用者操作が必要で無人実行できないため、**本番処理経路には含めません**。受入試験で集計結果を照合する用途には利用できます。

ただし、重要な成立条件があります。共有フォルダーについてケースで明示されているのはRBACだけであり、**排他的かつアトミックな公開操作**は保証されていません。したがって、後述するアトミック性試験に合格するまでは、「重複書き込み防止を保証できる」とは判定できません。

## 最小構成

```text
入力担当
   │ 完成済みCSVを配置
   ▼
input/ready/YYYY-MM-DD.csv
   │
   │ 既存自動化ランナーが日次起動
   ▼
work/<実行ID>/
   ├─ result.csv
   └─ manifest.json
   │
   │ 同一共有領域内で、上書き禁止のアトミック公開
   ▼
published/YYYY-MM-DD/
   ├─ result.csv
   └─ manifest.json

実行記録 ──> 自動化ランナーの保持ログ
```

`work`と`published`は、移動がコピー処理にならないよう、**同じ共有領域・同じファイルシステム上**に置きます。

### 各要件との対応

| 要件 | 対応 |
|---|---|
| 5万行CSVの部署別集計 | 集計ジョブがCSVを直接読み、部署別に集計 |
| 無人の定時実行 | 自動化ランナーの日次スケジュール |
| 障害後の再実行で重複書き込み防止 | 決定的な公開先、マニフェスト、上書き禁止のアトミック公開 |
| 実行ログ保持 | 自動化ランナーの保持ログ |
| 入出力のアクセス制限 | 共有フォルダーのRBAC |
| 追加製品を使わない | 既存ランナーと既存共有フォルダーのみを使用 |

## 再実行で重複させない処理規約

ここで保証する対象は、**同じ日次バッチの結果を公開領域へ二重に作成・追記・上書きしないこと**です。障害後に計算自体をやり直すことや、作業領域へ新しい一時ファイルを作ることは許容します。

### 1. バッチの識別

バッチには次の情報を持たせます。

- 対象日
- 入力ファイルの内容ハッシュ
- ジョブの版
- 入力行数
- 実行ID

公開先は対象日から一意に決めます。

```text
published/YYYY-MM-DD/
```

同じ対象日に別の入力内容が来た場合は、自動的に上書きせず、**競合エラーとして停止**します。

### 2. 入力を途中で読まない

入力担当は、アップロード中の名前から、完成後に`ready`領域へ切り替えます。ジョブは`ready`の入力だけを処理します。

さらに、ジョブは読み取り前後で入力のサイズまたはハッシュを確認し、処理中に内容が変わった場合は公開せず失敗させます。

### 3. 作業領域に完全な公開単位を作る

ジョブは固有の実行IDを持つ作業ディレクトリに、以下を作成します。

- `result.csv`：部署別集計結果
- `manifest.json`：入力ハッシュ、出力ハッシュ、行数、部署数、対象日、ジョブ版など

公開前に、少なくとも次を検証します。

- 入力データ行数が想定どおりである
- 各入力行が、定めた除外規則を除いて、いずれかの部署集計に一度だけ反映されている
- 部署別件数の合計が処理対象行数と一致する
- 集計対象の数値について、入力全体の統制合計と出力合計が一致する
- 出力CSVとマニフェストのハッシュが一致する

### 4. 公開は一度だけ行う

完成した作業ディレクトリ全体を、対象日の公開先へ移動します。この操作には次の両方が必要です。

- 読み手から見て、公開先が「存在しない」か「完全に存在する」かのどちらかになる
- 公開先がすでに存在する場合、置換せずに失敗する

単なる次の処理では不十分です。

```text
公開先が存在するか確認
→ 存在しなければ書き込む
```

確認と書き込みの間に別実行が割り込めるためです。

### 5. 再実行時の動作

公開先がすでに存在する場合は、結果を書き直しません。

| 状況 | 動作 |
|---|---|
| マニフェストの入力ハッシュ、ジョブ版、出力ハッシュが一致 | `SKIPPED_ALREADY_PUBLISHED`として正常終了。公開先への書込みなし |
| 同じ対象日だが入力ハッシュが異なる | `CONFLICT`として停止。既存結果を維持 |
| マニフェストが欠落・破損している | `CORRUPT_PUBLISHED_RESULT`として停止。自動修復や上書きはしない |
| 公開処理で別実行に先を越された | 既存マニフェストを照合し、一致ならスキップ、不一致なら競合停止 |

この方式なら、公開直後にプロセスが停止して成功ログを書けなかった場合でも、再実行は既存の完全な公開物を認識し、二度目の公開を行いません。

## ログに残す項目

ランナーの保持ログには、各実行について少なくとも次を出力します。CSVの個人情報や全明細は記録しません。

- 実行ID
- 対象日とスケジュールのタイムゾーン
- 開始・終了日時
- 入力ファイル名と入力ハッシュ
- 入力行数、正常行数、エラー行数
- 部署数、出力行数
- 入出力の統制合計
- 出力ハッシュ
- `SUCCESS`、`SKIPPED_ALREADY_PUBLISHED`、`CONFLICT`、`FAILED`などの終了状態
- 障害が発生した処理段階
- ジョブ版

ログ保持日数はケースに指定がないため、本番開始前に組織の要求日数を受入条件として固定し、その期間をランナーが満たすことを確認します。

## RBACの最小割当て

| 役割 | input/ready | work | published |
|---|---:|---:|---:|
| 入力担当 | 作成・配置 | 不可 | 不可 |
| 自動化用サービスアカウント | 読取り | 読書き | 新規公開に必要な書込み |
| 結果利用者 | 不可 | 不可 | 読取りのみ |
| 運用担当 | 必要範囲の読取り | 障害調査に必要な範囲 | 読取り |
| 権限管理者 | RBAC管理 | RBAC管理 | RBAC管理 |

サービスアカウントにはACL変更権限を与えません。また、結果利用者には公開先への更新・削除権限を与えません。

## 検証方法

### 1. 共有フォルダーのアトミック性試験 — 必須の前提試験

安全な試験領域で、2つの実行から同じ公開先に対して同時に公開を試みます。

合格条件は次のとおりです。

- 片方だけが公開に成功する
- もう片方は「すでに存在する」として失敗する
- 既存公開先が置換されない
- 読取り側から、CSVだけ、またはマニフェストだけの中途半端な状態が見えない
- 最終的な公開先は1つだけで、CSVとマニフェストが整合している

この試験に失敗した場合、以降の試験結果にかかわらず、重複防止要件は不合格です。

### 2. 正常系と5万行処理

既知の期待値を持つ5万行のCSVを配置し、利用者がログインしていない状態で定刻実行させます。

合格条件：

- ランナーが自動起動する
- 公開先が1つだけ作成される
- 部署ごとの結果が期待値と一致する
- 部署別件数の合計が5万行と一致する
- 数値項目の統制合計が一致する
- ランナーに開始、終了、入力・出力ハッシュ、件数、成功状態が保持される
- 表計算ソフトで同じ試験CSVを手動集計した結果とも一致する

### 3. 公開前の障害

次の各地点でジョブを強制停止し、同じ入力で再実行します。

- 入力読取り後
- 集計途中
- `result.csv`作成途中
- CSV作成後、マニフェスト作成前
- 公開操作の直前

合格条件：

- 公開先に部分ファイルが現れない
- 再実行後の公開先は1つだけ
- 出力内容が正常系の出力と同一
- 古い作業ファイルは公開対象にならない
- 初回障害と再実行成功の両方がログから追跡できる

### 4. 公開直後の障害

公開操作の完了直後、成功ログの記録前にジョブを停止し、再実行します。

合格条件：

- 再実行は既存マニフェストを認識する
- `SKIPPED_ALREADY_PUBLISHED`になる
- 公開CSVを書き直さない
- 公開先のファイル数、内容ハッシュ、更新情報が変化しない
- 最初の強制終了と、再実行時のスキップがログに残る

これは、障害後の重複防止を確認する最重要試験です。

### 5. 同時二重実行

同じ日付・同じ入力について、ランナーから2実行を同時に開始します。

合格条件：

- 公開先は1つだけ
- 片方が公開し、もう片方は既存結果を照合してスキップする
- 出力CSVに同じ部署が二重に追加されない
- どちらの実行結果もログで区別できる

### 6. 同一入力の再投入

成功済みのCSVを変更せずに再投入します。

合格条件：

- 公開先への書込みは行われない
- 結果は`SKIPPED_ALREADY_PUBLISHED`
- 入出力ハッシュが以前のマニフェストと一致する
- 既存出力の更新時刻や世代情報が、確認可能な範囲で変化しない

### 7. 同じ日付で内容の異なる入力

成功済みの日付に対し、1行だけ変更したCSVを投入します。

合格条件：

- `CONFLICT`で停止する
- 既存の公開結果を上書きしない
- 2つ目の公開結果を作らない
- 新旧の入力ハッシュがログに残る

訂正データの処理は通常の再実行と分離し、明示的な承認手順で既存公開物を撤回してから行います。

### 8. 破損検知

試験用公開先のマニフェスト欠落、ハッシュ不一致、CSV破損をそれぞれ作り、再実行します。

合格条件：

- 自動上書きしない
- 破損または競合として停止する
- 原因と対象日がログに残る

### 9. アクセス制御

各役割の資格情報で実際にアクセスを試します。

合格条件：

- 入力担当は作業・公開領域にアクセスできない
- 結果利用者は公開結果を読めるが、作成・変更・削除できない
- 結果利用者は入力と作業領域を読めない
- サービスアカウントは必要な領域だけにアクセスでき、権限設定を変更できない
- 権限のない利用者は入出力のどちらにもアクセスできない

### 10. ログ保持と性能

- ランナーやジョブプロセスを再起動した後も、過去の実行ログが取得できることを確認する
- 要求された保持期間を超えた試験ログが検索・取得できることを確認する
- 最大5万行、想定最大部署数、最大レコード長で処理時間とメモリーを測定する
- 次回の日次実行に影響しない時間内に終了することを確認する

## 最終的な合否判定

この構成は、**共有フォルダーが「上書き禁止のアトミック公開」を提供する場合**に、追加製品なしで要件を満たせます。自動化ランナーは定時実行とログ保持、スクリプトは集計と冪等性、共有フォルダーは保存とRBACを担当します。

一方、共有フォルダーがアトミックな排他作成・公開を提供せず、「存在確認後に通常書込み」しかできない場合は、同時実行の競合を排除できません。その場合、提示された承認済み機能だけでは重複書き込み防止を保証できず、追加の排他・トランザクション機能の承認、または要件の変更が必要です。表計算ソフトやランナーのログだけでは、この不足を補えません。
