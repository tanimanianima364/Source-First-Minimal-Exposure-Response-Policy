## 結論

提示された revision r1 の範囲では、最小の本番構成は次の3要素です。

1. **既存の承認済み自動化ランナー**：毎日の定時起動と実行ログ保持  
2. **1本の集計バッチスクリプト**：CSV検証、部署別集計、再実行時の冪等制御  
3. **既存の共有フォルダ**：入力、作業、確定出力、冪等制御情報を分離し、ロール別に権限設定  

インストール済みスプレッドシートは、無人実行、永続的な実行ログ、再実行時の重複防止を提供できないため、**本番処理経路には含めません**。受入試験で集計結果を手動照合する用途には使えます。

ただし、提示情報では共有フォルダが「原子的な非上書き作成」を保証するか不明です。したがって、次の構成が要件を厳密に満たすのは、共有フォルダ上で以下が可能であることを確認できた場合です。

- 完成済み一時ファイルを、既存ファイルを上書きせず原子的に確定できる
- 同じ名前を同時に作ろうとした場合、成功する実行が必ず1つだけになる
- 確定ファイルが利用者から見えるときは、未完成状態ではなく完全な状態である

この条件を満たさない場合、単純な「存在確認後に書く」方式には競合時間帯があるため、承認済み構成だけで重複書き込み防止を厳密には証明できません。

## 最小構成

```text
CSV提供者
   |
   v
/input/drop                  提供者は書込み、ランナーは読取り
   |
   v
自動化ランナーの定時ジョブ
  ・入力固定化
  ・形式検証
  ・部署別集計
  ・整合性検証
  ・冪等な確定処理
   |
   +--> /work                ランナー専用の一時領域
   +--> /control             処理対象の識別情報と完了記録
   +--> /output              確定した部署別集計CSV
   |
   +--> ランナー内の永続実行ログ

/output
   |
   v
集計結果の利用者              読取り専用
```

共有フォルダ内は、少なくとも次の4領域に分けます。

| 領域 | 用途 |
|---|---|
| `/input/drop` | CSVの受領。一時名でアップロードし、完了マーカーまたは確定名で受領完了を示す |
| `/work` | 受領済み入力の固定コピー、集計中の一時出力。ランナーだけがアクセス |
| `/control` | バッチ識別情報、入力ハッシュ、処理ルール版、完了記録 |
| `/output` | 利用者に公開する確定済みCSVだけを格納 |

`/work` と `/output` は、原子的な確定操作を成立させるため、可能な限り**同一の共有ボリューム内**に置きます。

## 重複書き込みを防ぐ処理方式

保証するのは「ジョブが一度しか起動しないこと」ではなく、ジョブが複数回起動しても、**外部に確定する結果が1回だけになること**です。

### 1. 処理単位を固定する

1日1ファイルを前提に、処理単位となるバッチIDを次のように固定します。

```text
バッチID = データ種別 + 業務日
例: department-source_2026-09-27
```

バッチIDには、実行時刻、ランナーの実行ID、再試行回数を使用しません。これらを使うと、再実行のたびに別出力になってしまいます。

入力ファイルについては、受領後の固定コピーから暗号学的ハッシュを計算します。制御情報には次を保持します。

- バッチID
- 入力ファイルのハッシュ
- 集計ルールのバージョン
- 出力ファイルのハッシュ
- 入力データ行数
- 部署数
- 入力全体の集計値
- 出力全体の集計値

### 2. 入力を固定する

CSV提供者は一時名でアップロードし、完了後に確定名へ変更するか、完了マーカーを置きます。ランナーは未完了ファイルを処理しません。

処理開始時にランナー専用の `/work` へ入力を固定し、以後はその固定コピーだけを使用します。これにより、処理中に提供者が元ファイルを変更しても集計結果が変化しません。

### 3. 決定的な出力を作る

同じ入力と同じ集計ルールからは常に同じバイト列になるよう、次を固定します。

- 部署の並び順
- CSVの文字コード
- 区切り文字、引用符、改行形式
- 数値の桁数と丸め方法
- 空値、不正値の扱い
- ヘッダー名と列順

不正行を黙って除外すると再現性と監査性が下がるため、最小構成では、必須列欠落や不正数値があれば**バッチ全体を失敗**させ、確定出力を作らない方式が安全です。

### 4. バッチの入力を一度だけ確定する

集計候補の検証後、次の制御ファイルを原子的な「既存なら失敗」で作成します。

```text
/control/<バッチID>.claim
```

内容は入力ハッシュと集計ルール版です。

- ファイルがなければ作成
- 同じ内容ですでに存在すれば、同じ入力の再実行として続行
- 入力ハッシュまたは集計ルール版が異なれば、同じバッチIDの競合として停止
- 既存の制御ファイルを上書きしない

これにより、同じ業務日のファイルが差し替えられた場合も、既存結果を黙って置換しません。修正版は明示的な版番号を持つ別バッチとして扱います。

### 5. 出力を一度だけ確定する

集計結果は、まず `/work` に実行固有の一時名で完全に書き出し、クローズと検証を完了させます。その後、次の固定パスへ「既存なら失敗」で原子的に公開します。

```text
/output/<バッチID>.csv
```

結果は次のように扱います。

| 状態 | 動作 |
|---|---|
| 出力が存在しない | 一時ファイルを原子的に確定 |
| 出力が存在し、期待する出力ハッシュと一致 | すでに確定済みとして書込みを行わず正常終了 |
| 出力が存在するがハッシュが異なる | 競合として異常終了。既存ファイルを上書きしない |
| 出力はあるが完了記録がない | 出力を再計算して一致を確認し、完了記録だけを復旧 |
| 完了記録も出力も正しい | `ALREADY_COMMITTED` として何も変更せず正常終了 |

確定後に、次を原子的に作成します。

```text
/control/<バッチID>.done
```

`.done` の内容も入力・出力ハッシュなどの決定的な情報だけにします。実行IDや現在時刻のように再実行ごとに変わる値はランナーのログに記録し、完了記録の同一性判定には使いません。

### 6. 障害地点ごとの結果

| 障害地点 | 再実行時の結果 |
|---|---|
| 入力固定化前 | 改めて入力を固定して開始 |
| 集計途中 | 未確定の一時ファイルを無視または削除して再計算 |
| `.claim` 作成後、出力確定前 | 同じ入力ハッシュで処理を継続 |
| 出力確定直後、`.done` 作成前 | 既存出力を検証し、出力は再書込みせず `.done` だけ復旧 |
| `.done` 作成後 | 書込みを行わず確定済みとして終了 |
| 同一バッチの同時実行 | 1実行だけが確定操作に成功し、他は既存結果を検証して終了 |
| 同じバッチIDで異なる入力 | `.claim` の不一致で停止し、既存出力は維持 |

## 実行ログ

ランナーが保持する実行ログには、少なくとも次を構造化して出力します。

- ランナー実行ID
- バッチID
- 予定実行時刻、実際の開始・終了時刻
- 入力ファイル名と入力ハッシュ
- 読み取ったデータ行数
- 正常行数、不正行数
- 部署数
- 入力総計と出力総計
- 出力ハッシュ
- 最終状態
- エラーコードとエラー発生段階

最終状態は、例えば次のように区別します。

- `SUCCESS_COMMITTED`：今回の実行で初めて確定
- `SUCCESS_ALREADY_COMMITTED`：既存結果を検証し、書込みなし
- `FAILED_VALIDATION`：入力または集計結果が不正
- `FAILED_CONFLICT`：同じバッチIDで異なる入力または出力
- `FAILED_INFRASTRUCTURE`：共有フォルダなどの障害

CSVの明細値や個人情報はログに出さず、ハッシュ、件数、集計値などの監査用メタデータに限定します。

保存期間は提示されていないため、組織の必要保存期間をランナーに設定し、その期間より前にログが消えないことを受入条件にします。

## アクセス権の最小設定

個人アカウントではなく、ランナー専用のサービスアカウントを使用します。

| ロール | `/input/drop` | `/work` | `/output` | `/control` | ランナーのログ・操作 |
|---|---:|---:|---:|---:|---:|
| CSV提供者 | 書込み | なし | なし | なし | なし |
| ランナー用サービスアカウント | 読取り・受領処理 | 読書き | 作成・検証 | 作成・検証 | 実行・ログ出力 |
| 結果利用者 | なし | なし | 読取りのみ | 原則なし | なし |
| 運用担当者 | 原則読取りのみ | なし | 読取りのみ | 読取りのみ | 実行、再実行、ログ読取り |
| 監査担当者 | なし | なし | 必要に応じ読取り | 読取りのみ | ログ読取り |
| 権限管理者 | 権限設定のみ | 権限設定のみ | 権限設定のみ | 権限設定のみ | 管理権限 |

共有フォルダの権限モデルが対応する場合、ランナーの `/output` 権限は「新規作成と読取りは可能だが、既存ファイルの上書き・削除は不可」にします。そこまで細かく設定できない場合でも、少なくともランナー以外の利用者には出力書込み権限を与えません。

## 受入試験

### 必須試験一覧

| 要件 | 試験 | 合格条件 |
|---|---|---|
| 原子的確定の前提 | 同じファイル名に対し複数実行から同時に非上書き作成 | 成功は必ず1実行だけ。確定ファイルは完全な内容で、部分ファイルが公開されない |
| 集計の正しさ | 既知の部署別合計を持つテストCSVを処理 | 全部署の件数・金額が期待値と一致 |
| 50,000行対応 | 50,000データ行のCSVを定時ジョブと同じ条件で処理 | 日次処理枠内で完了し、メモリ・一時領域不足がない |
| 全体整合性 | 入力の件数・総計と、部署別出力の件数・総計を比較 | 部署別件数の合計が入力正常行数と一致し、部署別金額合計が入力総計と一致 |
| 無人実行 | 利用者がログインしていない状態でスケジュール実行 | 人の操作やスプレッドシート操作なしで出力とログが生成される |
| 同一入力の再実行 | 正常完了後、同じ入力を複数回再実行 | 出力は1ファイルだけ。出力ハッシュ、サイズ、更新時刻が変わらず、ログは `ALREADY_COMMITTED` |
| 同時実行 | 同じバッチを2実行以上同時起動 | 確定出力は1つだけ。失敗側または待機側が上書きしない |
| 入力差し替え | 同じバッチIDで内容の異なるCSVを投入 | 競合エラーとなり、既存出力は変更されない |
| 不正入力 | 必須列欠落、不正数値、壊れたCSVを投入 | 確定出力なし。エラー内容がログに残る |
| 出力改ざん | 確定出力の内容を試験的に変更して再実行 | ハッシュ不一致で停止し、上書き修復をしない |
| ログ保持 | 成功、失敗、再実行スキップを発生させ、保存期間後も検索 | バッチIDと実行IDで追跡でき、必要期間保持される |
| アクセス制御 | 各ロールの資格情報で許可・禁止操作を実行 | 許可された操作だけ成功し、禁止操作は実際に拒否される |

### 障害注入試験

少なくとも次の地点で実行プロセスを強制終了し、その後同じバッチを再実行します。

1. 入力固定化直後  
2. 集計一時ファイル作成中  
3. `.claim` 作成直後  
4. 出力の原子的確定直前  
5. 出力確定直後、`.done` 作成前  
6. `.done` 作成直後  

全ケースの合格条件は共通です。

- `/output` に確定ファイルが最大1つだけ存在する
- 確定ファイルは期待ハッシュと一致する
- 部分的なCSVが利用者に公開されない
- 再実行後に `.done` が正しい状態になる
- 既存の確定出力を再書込みしない
- 最初の失敗と再実行結果の双方がランナーのログに残る

集計値の独立確認には、インストール済みスプレッドシートへテストCSVを手動で取り込み、部署別合計を比較できます。これは受入試験用であり、日次運用には依存させません。

## 本番移行の判定条件

次の3点をすべて実証できれば、この最小構成で要件を満たせます。

1. 共有フォルダが、既存ファイルを上書きしない原子的な確定操作を提供する  
2. ランナーのログが必要期間保持され、成功、失敗、再実行スキップを追跡できる  
3. 入力提供者、ランナー、出力利用者、運用・監査担当者の権限分離が実操作試験で成立する  

特に1が成立しない場合、ファイルの事前存在確認だけでは同時実行と障害境界の競合を排除できません。その場合は、現時点で承認されている製品だけでは「重複書き込み防止」を厳密には満たさないため、本番移行は不可と判定するのが妥当です。
